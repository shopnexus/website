# Round two: surfacing `understood` / `probes`

## What changed

1. **Regenerated the API client** (`pnpm gen:api`, same source as round one: the gateway's
   served spec via `../server/api/openapi.gen.yaml`). `ListingPage` in `types.gen.ts`
   already carried `understood: string` and `probes: Array<string>` going into this round
   (the server had shipped them ahead of this regen), so the only real diff from
   regenerating now is a new `ListingQueuePage` type — the admin moderation queue's
   `GET /admin/listings` response now correctly excludes the two search fields, since that
   worklist takes no query. `src/api/generated/types.gen.ts` and `index.ts` changed;
   `sdk.gen.ts`, `@tanstack/react-query.gen.ts` and `ws-events.ts` had no diff.

2. **Threaded the two fields through the feed hook**
   (`src/hooks/api/useCatalog.ts`, `useListingsFeed`). `understood` and `probes` are
   root-level siblings of `data`/`meta` on `ListingPage`, not per-item — and every page of
   an infinite query repeats them (they describe the query, not the page) — so I read them
   off `query.data.pages[0]` next to the existing `totalCountOf(query.data)` pattern,
   defaulting to `""`/`[]` before the first page lands. `unwrapData` was not usable here:
   it strips the envelope down to just `data`, which would have thrown these two away.

3. **New component** `src/app/search/_components/SearchUnderstanding.tsx`, wired into
   `src/app/search/page.tsx` between `SearchToolbar` (the "found N results for X" line)
   and `ActiveFilterChips`. Renders:
   - `understood` as a plain-text sentence (never `dangerouslySetInnerHTML` — it is
     model-written, so it is treated exactly like any other untrusted string) with a small
     `auto_awesome` icon, in `text-body-sm text-on-surface-variant` — the same quiet
     register `SearchToolbar` already uses for secondary text.
   - the *corrected* subset of `probes` as a row of plain, non-interactive `<span>` pills
     (`rounded-full border border-outline-variant/30 bg-surface-container-low`), preceded
     by a small "Cũng tìm theo:" label.
   Returns `null` outright when there is nothing to say.

## Judgment calls

- **Not `Chip`.** `src/components/ui/Chip.tsx` renders a `<button>` with `cursor-pointer`
  and an optional `onRemove` × — it is built for a *selectable or removable* filter
  (that's exactly how `ActiveFilterChips` next to this component uses it). A probe phrase
  is neither: it's not a filter the shopper chose and clicking it does nothing, so wrapping
  it in a button would be a lie about affordance. I used plain `<span>`s instead, styled
  close to the read-only tag pill in `src/components/ui/TagRail.tsx` (border +
  `bg-surface`/`bg-surface-container-low`, `text-label-sm`, no hover state) minus the
  `<Link>` since these aren't navigable.

- **Excluding the shopper's own words from the chip row, not just "distinguishing" them.**
  The task's constraint 4 allows visually distinguishing the shopper's words from
  corrections, as long as the distinction is honest. I went one step further: the raw
  query is filtered out of the displayed `probes` entirely
  (`probe.trim().toLowerCase() !== search.query.trim().toLowerCase()`), because it is
  already visible verbatim as the toolbar's `"${search.query}"` subject line one line
  above — repeating it as a chip would add a redundant pill with no information, and if it
  ever sorted first it would read exactly like "corrected to: ao thu unilo", which is the
  literal query. This is also what makes state 3 (probes = shopper's words only) fall out
  for free: the corrected list is then empty and the whole chips row doesn't render.

- **Two independent gates, not one.** `understood` and the corrected-`probes` list are
  checked separately (`if (!understood && corrected.length === 0) return null`), and each
  renders independently inside. This covers all four states named in the task without
  special-casing them:
  - no query → both `understood` and `probes` are `""`/`[]` from the server, `corrected`
    is empty → component returns `null`.
  - query, model produced nothing usable → `understood` is `""` but real corrections
    might still exist in `probes` (or not); either sub-block renders on its own merit, so
    an empty `understood` never gets backfilled with invented text.
  - query, nothing was corrected (`probes` = [shopper's words]) → `corrected` is empty, so
    the chip row is skipped even if `understood` happens to be non-empty (a clean query can
    still get a one-line gloss with no chips to back it, which is not a lie — it's not
    claiming a correction happened).
  - query with both → full display, matching the two worked examples in the task
    (`ao thu unilo` → `áo thun uniqlo`, `áo thun`; `dien thoai cu duoi 3 trieu` → `điện
    thoại cũ`, `điện thoại giá rẻ`).

- **Placement.** Directly under `SearchToolbar`'s headline rather than inside it — kept as
  its own file/component to match the page's existing decomposition (toolbar = count +
  sort, this = query interpretation, `ActiveFilterChips` = active filters, `SearchResults`
  = grid), and so it can return `null` cleanly without `SearchToolbar` growing a second
  responsibility.

- **Verified against the live gateway**, not just the type system:
  ```
  $ curl -s "http://localhost:5000/api/v1/listings?limit=1" | …
  understood= '' probes= []
  $ curl -s "http://localhost:5000/api/v1/listings?limit=1&q=ao+thu+unilo" | …
  understood= 'Bạn đang tìm kiếm áo thun thương hiệu Uniqlo.' probes= ['áo thun uniqlo', 'áo thun', 'ao thu unilo']
  ```
  confirming the browse case is genuinely `""`/`[]` (not just my assumption) and that the
  shopper's raw words really do come back verbatim inside `probes`, which is what my
  exclusion filter matches against.
